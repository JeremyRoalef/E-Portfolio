Chamber Fall - Agile Development Lifecycle

A detailed breakdown of the development of my group's game, Chamber Fall.

Chamber Fall is a roguelike first-person shooter where players choose from three distinct characters, each with unique weapons and abilities, and battle through randomized chambers of enemies, augments, and bosses to survive as far as possible.

In this project, Michael, Aiden, and I set out to discover how to follow the Agile Development lifecycle to develop Chamber Fall. We must determine our product backlog, sprints, and contingency plans for unforeseen errors. We must learn how to handle GitHub branches, resolve merging conflicts, and learn how to play into each other's strengths.

Our project will be broken up into five parts, one part for each sprint.

💻 GitHub

Team:

    Jeremy Roalef: Game Programmer, Systems Designer
    Michael Roberts: Game Programmer, Enemy Programming & Design
    Aiden Longueville: Assets Design

Tech: Unity, C#, Jira, GitHub

Course: CITA 412: Advanced Game Design & Application

Instructor: Professor Awedat


Sprint 1 was critical to our game's setup. We needed a first-person shooter template ready, sample assets, enemies to interact with, and a chamber design system that we may implement into the actual game. I will mainly discuss my role in this sprint: setting up the first-person template and the procedurally generated chamber design system.

First-Person Shooter Template

Since our game was set up in Unity, we had quick access to a free FPS template from which we could quickly work. I installed the template from Unity's asset store and got to work. The first thing I needed to do was configure the input system. I created an Input Manager script that my team could easily use to gather player input for our game.

After setting up the input manager, I customized the player prefab that came with the FPS template. My changes were minimal, but the main thing was altering how the input was collected using my new input manager.


Procedurally Generated Chamber Design System

Making the chamber system was one of the most thought-provoking programming exercises I accomplished. I learned how to utilize custom structs for grid positions, scriptable objects for chamber data, Breadth-First search / A* pathfinding algorithms to connect chambers, and Prim's algorithm to develop a minimum-spanning tree, all within two weeks.

The image below depicts the result of my map generation system. The yellow lines represent placeholder hallway connectors to the chambers, the grey boxes represent the chambers, and the blue box is a placeholder for the boss chamber

Making the procedural generation taught me a valuable lesson in code optimization. When I first ran my scripts, it took a combined 11 minutes to run. It was the first time I saw the true inefficiencies of my code. Trying to figure out what exactly caused the poor performance was a challenging endeavor. In the end, I learned how to debug code efficiently and how to utilize large language models to help point me in the right direction for code inefficiencies.
